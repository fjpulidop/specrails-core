# C4–C6 piece integration decisions

These decisions resolve adapter details before their implementation. The public
definition remains data; provider transports, journal access, accounting and
durability are supplied at composition time.

- `RoleStatePort` is bound to a run, execution scope and node. The legacy role
  invoker defaults to its existing file adapter; engine pieces supply isolated
  durable storage. Routing, compact policy, context snapshots and the single
  structured repair continue through `createRoleInvoker`.
- Provider invocation start/settlement and budget reads use an adapter to the
  existing `WorkflowStepContext`. A piece never synthesizes usage or counts a
  completed invocation twice. Missing provider measurements remain unknown.
- A prompt which pauses after `LOOP_BLOCKED` persists its provider result before
  raising the interrupt. Reentry reads that result before requesting the answer;
  it does not repeat the provider call. Answering permits a bounded continuation
  in the same node with the reply added to the prompt. The invocation store is
  scoped to the physical attempt and invocation ordinal, not a cross-run cache.
- Captures and expression regexes execute a constant VM script with only string
  inputs, a 50 ms timeout, no dynamic code generation and a 32,000 character
  input cap. Pattern length stays at 200; no flags or user JavaScript are accepted.
- Verification command execution and receipt construction are extracted behind
  a journal-independent evidence adapter. Legacy verification preserves its
  journal transaction and receipt file format. Ledger-only runs never create
  `state.json`; they persist started and completed checks through the adapter.
- OpenSpec archive retains the real pinned CLI and recoverable write-set
  publication. Its write-set lives in an explicitly owned node directory; the
  general piece does not invoke the implementation journal acceptance gate.
  The enclosing definition still owns verification and completion requirements.
- `end.outcome` remains `success` or `failure`. Optional `end.exit` selects an
  explicitly declared component exit, preserving independent business success
  and parent routing. It is rejected outside component bodies.
- Each implementation instance owns a journal binding. The standalone root
  implementation preserves the original context/change. Components and map
  branches derive a stable run ID and change name from the parent run and
  execution scope; their journals are sibling pipeline directories with explicit
  parent ownership recorded in SQLite. Ticket/repository items narrow the frozen
  context; arbitrary items without an admitted scope are rejected. Backlog and
  host delivery ownership remain unchanged. Fork restores only registered
  unfinished instances and rebinds their derived identities to the new parent run.
- Explicit `unverified` verification may produce an exception receipt with
  uncovered repositories. It never installs `$verified` for zero checks or
  uncovered repositories. A shell evidence receipt never installs `$verified`.
- A free prompt admits at most 32 human continuation rounds per node visit;
  each provider invocation still uses the run's durable budget. This bounds
  replay notes even when the definition has no token or cost limit.
- The decider retains Desktop's strict evidence-oriented instructions, including
  the rule that a claimed sentinel alone does not prove goal completion. Core's
  result schema uses `verdict` and `reason`; human blocking remains an interrupt,
  and no-progress termination remains unsuccessful evidence, never verification.
- Native implementation child checkpoints publish a bounded manifest of immutable
  journal, verification, active/archived change and main-spec bytes. Blobs are
  flushed before the SQLite terminal transaction; fork reads the manifest at
  the selected cut, never a later mutable journal. The manifest limit is 1 MiB,
  at most 8192 files/256 MiB referenced bytes, and 1,750,000 bytes for the native
  child state envelope. Excess state fails explicitly; recovery data is not
  truncated. For an unfinished instance, fork rebinds the native verification plan and clears receipt,
  acceptance and archive approval. Architecture/development remain reusable only
  when their cut phase was complete.
- A fork's private main-spec baseline permits real pinned-CLI archive preparation
  after the source has progressed. Publication still validates current before
  or after images and refuses unrelated conflicting edits. The source journal,
  database and evidence stay byte-for-byte unchanged. The worktree is shared:
  changes from the fork may make a fresh source inspection stale, requiring
  normal revalidation if that original run resumes.
- For an incomplete implementation fork, archive preserves the source change ID
  only in the pinned CLI's exact autogenerated `Purpose` placeholder. The source
  identity is captured in the private baseline manifest and inherited by later
  forks. Authored purpose text and requirement bytes are never normalized; a
  differing current specification still blocks publication. Completed native
  implementations at the chosen parent cut inherit historical evidence instead
  of restoring their journals or repeating provider calls.
- Native developer/fixer phases share the role session state of their enclosing
  implementation scope. Separate component/map scopes never share those
  sessions. Verification commands are narrowed to each item's frozen repositories.
- Scoped implementation receipts retain their native evidence but do not install
  global verification. Component and Batch templates verify the parent candidate
  after the child/join and require verified delivery. Runtime exclusions persist
  only explicit parent/child journals, declared OpenSpec artifacts and the exact
  project-store SQLite/WAL/SHM paths; legacy journals omit these additive fields.
